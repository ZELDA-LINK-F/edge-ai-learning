# 二、内存与资源管理 ⭐（边缘 AI 的第一课）

## 2.1 统一内存模型
| | |
|---|---|
| **是什么** | CPU 和 GPU 共享同一块物理内存，**没有独立显存** |
| **关键数据** | 总 **7.62 GB**；实测空闲占用 2.3G；可用 4.8G |
| **对比 PC** | PC：8G 内存 + 8G 显存 = 16G 可用 ｜ Jetson：**7.62G 共用** |
| **为什么重要** | 模型占的内存和系统占的内存**抢同一块** → 任何服务吃内存都会直接让模型跑不动 |
| **我的实测** | ASR 服务占 4.3G 时，本地模型加载直接报 `cudaMalloc failed: out of memory` |
| **要能回答** | 为什么"显存还剩多少"这个问题在这块板子上**没有意义**？ |
| **⚠️ 易错点** | 按 PC 习惯把"显存"和"内存"分开算 |

## 2.2 内存账本
| | |
|---|---|
| **是什么** | 搞清楚每一 MB 内存被谁占着 |
| **工具** | `free -h` ｜ `ps -eo rss,comm --sort=-rss` ｜ `sudo tegrastats` ｜ `systemctl show -p MemoryCurrent` |
| **关键** | **看 available，不看 free** —— buff/cache 是缓存，随时能释放 |
| **我的实测账本** | 系统基础 1.0G ｜ 桌面 GUI 450M ｜ 常驻服务 600M ｜ 模型 1.1~3.2G |
| **为什么重要** | 不知道谁在占，就无法回答"模型为什么跑不起来" |
| **要能回答** | 现在谁在占内存？哪块能省？省多少？ |
| **⚠️ 易错点** | 把 buff/cache 当成"已用内存"，误判"内存不够了" |

## 2.3 每参数字节 ⭐
| | |
|---|---|
| **是什么** | 每个模型参数占几个字节，由数值精度决定 |
| **关键数据** | FP32 = 4B ｜ FP16 = 2B ｜ INT8 = 1B ｜ Q4（4bit）= 0.5B |
| **公式** | **权重内存 ≈ 参数量 × 每参数字节** |
| **我的实测** | ResNet18 = 1170 万参数 → FP16 引擎 **23.8MB**、INT8 引擎 **11.7MB**（精确对上） |
| **LLM 例子** | 1.5B 参数 × 0.5B(Q4) ≈ 0.75G 权重，**但实测加载后占 2.1G** |
| **为什么重要** | 直接决定"这个模型能不能装进 8GB" |
| **要能回答** | ① 7B 模型 Q4 大概占多少内存？② 为什么实际占用总大于理论权重？ |
| **⚠️ 易错点** | 只算权重，忘了 **KV 缓存 + CUDA 上下文 + 框架开销**（通常多出 0.8~1.3G） |

## 2.4 常驻 vs 按需
| | |
|---|---|
| **是什么** | 服务一直驻留内存换响应速度 ←→ 用完卸载换空间 |
| **我的实测** | 判难度器**常驻 147M** → 每次判定 **60ms**；若不常驻要重载 **1.8G / 330ms** |
| **另一例** | ASR 服务常驻 3.0G，被设计成**空闲 900 秒自动退出**把内存还回去 |
| **判断标准** | 调用频率 × 单次节省的时间 **>** 常驻的内存代价？ |
| **要能回答** | 哪些服务该常驻？哪些该按需？依据是什么？ |
| **⚠️ 易错点** | 以为"常驻就是浪费内存"或"按需就是最优" —— 要算频率 |

## 2.5 内存碎片 ⭐
| | |
|---|---|
| **是什么** | 内存池被切成小块，找不到足够大的**连续**空间 |
| **现象** | `free` 显示还有 3~5G 可用，加载模型却报 `unable to allocate CUDA0 buffer` |
| **指标** | tegrastats 里的 **lfb**（最大连续空闲块） |
| **我的实测** | 清理前 `lfb 2x4MB`（可用 3.2G）→ 清理后 `lfb 152x4MB`（可用 5.0G） |
| **解法** | `sudo sysctl vm.drop_caches=3` → 还不行就**重启**（最彻底） |
| **为什么 CUDA 敏感** | 显卡驱动需要**连续物理内存块**，碎片化就分配不出来 |
| **要能回答** | 为什么"内存够"还会分配失败？三种解法是什么？ |
| **⚠️ 易错点** | 只看 `free` 的 available 就下结论 |

## 2.6 KV 缓存与上下文
| | |
|---|---|
| **是什么** | 模型"记住上下文"所需要的内存，随上下文长度**线性增长** |
| **关键数据** | qwen-fast 模型上限 32768，但实际只用了 **4096**（`ollama ps` 里能看到） |
| **关系式** | `num_ctx` 翻倍 → KV 缓存翻倍 |
| **为什么重要** | RAG 往提示里塞资料时，这直接决定"能塞多少"和"慢多少" |
| **要能回答** | 为什么不把上下文开满？开大有哪两个代价？ |
| **⚠️ 易错点** | 以为"上下文只是软件设置，不占内存" |

## 2.7 swap / zram
| | |
|---|---|
| **是什么** | 内存不够时，把不常用的数据换到别处存放 |
| **我的实测** | 8G swapfile（在 NVMe 上）+ 6×635M zram（**压缩内存**） |
| **关键** | swap 是**保命手段，不是提速手段**；zram 是"用 CPU 换空间" |
| **观察法** | SWAP 被大量使用 = 系统内存紧张 |
| **我的实测对比** | ASR 服务开着时 SWAP 用 **1.5G**；禁用后 SWAP = **0** |
| **要能回答** | 看到 SWAP 被用说明什么？该做什么？ |
| **⚠️ 易错点** | 以为"有 swap 就不怕内存不够" —— 它会让速度暴跌 |

# 三、模型与推理基础

## 3.1 参数量与量化等级
| | |
|---|---|
| **是什么** | "参数量"= 模型有多少个可调数字；"量化等级"= 每个数字用多少位存 |
| **常见等级** | FP32（原始）｜ FP16 ｜ Q8 ｜ **Q4_K_M**（常用）｜ INT8 |
| **记忆法** | B = 十亿参数（1.5B = 15 亿）；Q4 的 "4" = 4 bit = 0.5 字节 |
| **前人结论** | 8GB 上 LLM 的**甜点区是 0.5B ~ 4B** |
| **要能回答** | 为什么 7B 模型在这块板子上"能跑但难受"？ |

## 3.2 推理 vs 训练
| | |
|---|---|
| **是什么** | **推理 = 用模型**（输入→输出）；**训练 = 造模型**（调参数） |
| **为什么重要** | 边缘 AI **只做推理**，两者的优化手段完全不同 |
| **推理的优化手段** | 量化、算子融合、批处理、编译优化、内存调度 |
| **训练的优化手段** | 数据质量、算力规模、算法设计 |
| **要能回答** | 为什么"边缘 AI 工程师"不需要会训练大模型？ |

## 3.3 延迟 vs 吞吐 ⭐
| | |
|---|---|
| **是什么** | **延迟** = 一次请求要多久；**吞吐** = 每秒能处理多少 |
| **冲突关系** | 提高吞吐常常牺牲延迟（凑批、缓冲、排队） |
| **我的实测** | batch 1 → **0.99 ms/次**；batch 8 → **3.60 ms/次**，但每张图只要 **0.45 ms** |
| **应用判断** | 摄像头实时（33ms/帧）→ 延迟优先 ｜ 离线批处理 → 吞吐优先 |
| **要能回答** | 摄像头 30 帧场景，该选大 batch 还是小 batch？为什么？ |
| **⚠️ 易错点** | 以为"优化"只有一个方向 —— 选错方向等于白干 |

## 3.4 token 与上下文预算 ⭐
| | |
|---|---|
| **是什么** | token 是模型处理文本的最小单位（不是字，也不是词） |
| **我的实测** | **固定开销 ~30 token/次**（聊天模板）；中文 **0.60 token/汉字**；英文 0.21 token/字符 |
| **换算** | 1500 token ≈ **2500 个汉字** |
| **正确做法** | **直接量，不要估** —— 响应里的 `prompt_eval_count` 就是真实值 |
| **前人教训** | 他按 1.5 token/汉字估，实测 0.87，**高估 72%**，导致上下文预算算错 |
| **要能回答** | 为什么"你好"两个字要花 30 个 token？ |
| **⚠️ 易错点** | 用"1 汉字≈N token"的经验值拍脑袋；忘了固定开销 |

## 3.5 batch ⭐
| | |
|---|---|
| **是什么** | 一次推理同时处理几个样本 |
| **为什么有效** | ① GPU 有 1024 个核心，单张喂不饱；② **固定开销被摊薄**（内核启动、权重加载、主机发指令） |
| **我的实测** | batch 1/4/8 → 总耗时 **0.991 / 2.029 / 3.602 ms**；每张成本 **0.991 / 0.507 / 0.450 ms** |
| **代价** | 显存占用上升、单次延迟上升、边际收益递减 |
| **⚠️ qps 陷阱** | `Throughput(qps)` 要 **× batch** 才是真实图片吞吐（1005.8×1=1006；491.9×4=1968） |
| **要能回答** | batch 4 的总耗时为什么**不是** batch 1 的 4 倍？ |
| **⚠️ 易错点** | 直接看 qps 数字，得出"batch 越大吞吐越低"的错误结论 |

## 3.6 PyTorch 基础 🟡
| | |
|---|---|
| **是什么** | 最主流的深度学习框架（做推理也常用它当**基线对照**） |
| **需要的部分** | 张量、`.eval()`、`.cuda()`、`torch.no_grad()`、`torch.onnx.export` |
| **为什么需要 eval()** | BatchNorm / Dropout 在训练和推理时**行为不同**，不切换会得到错误结果 |
| **要能回答** | 为什么导出 ONNX 前必须 `model.eval()`？ |
| **⚠️ 易错点** | 忘了 eval()，导出的模型行为错误却不报错 |

## 3.7 模型文件格式
| | |
|---|---|
| **三种格式** | `.pth` / `.pt` = PyTorch 权重 ｜ `.onnx` = 通用中间格式 ｜ `.engine` = TensorRT 编译产物 |
| **类比** | 源码（PyTorch）→ 汇编（ONNX）→ 可执行文件（engine） |
| **关键区别** | ONNX **跨平台**；engine **绑定硬件和 TensorRT 版本** |
| **要能回答** | 部署时该发布哪个文件？为什么不能只发 engine？ |

# 四、TensorRT 与推理加速 ⭐（核心竞争力）

## 4.1 编译型 vs 解释型 ⭐
| | |
|---|---|
| **是什么** | 解释型=逐个算子执行；编译型=先把整张图编译成最优内核 |
| **解释型的成本** | 每个算子都要"解释→启动内核→同步→下一个"；ResNet18 有 49 个节点 = 49 次循环 |
| **编译型的收益** | 内核更少、每次做更多事、中间结果不落地 |
| **我的实测** | PyTorch GPU **6.3 ms** → TensorRT FP32 **1.57 ms**（4 倍） |
| **类比** | 解释型 = 每说一句找一个翻译；编译型 = 整篇先翻译好 |
| **要能回答** | TensorRT 快，具体快在什么地方？（说出两个成本来源） |

## 4.2 ONNX ⭐
| | |
|---|---|
| **是什么** | 模型的**通用中间格式**，让不同框架训练的模型能交给同一个推理引擎 |
| **关键参数** | `opset_version`（规范版本）｜ `input_names/output_names`（推理时按名字取张量） |
| **⭐ 最关键** | 导出需要**示例输入 x** —— 因为 PyTorch 是"**追踪执行**"，不是"编译" |
| **好处** | 从"会执行的代码"变成"**静态计算图**" —— 这是能加速的前提 |
| **dynamic_axes** | 不写 → batch 被**钉死**；要变 batch 必须写 `dynamic_axes={"input":{0:"batch"}}` |
| **我的实测** | 没写 dynamic_axes → 想加 batch 时报 `Static model does not take explicit shapes` |
| **要能回答** | ① 为什么导出时要给一个示例输入？② 不写 dynamic_axes 会有什么后果？ |
| **⚠️ 易错点** | 导出前忘了 `model.eval()`；导出后不验证数值（我们的误差 4e-06） |

## 4.3 trtexec
| | |
|---|---|
| **是什么** | TensorRT 的命令行工具：编译 engine + 测量性能 |
| **常用参数** | `--onnx=` `--saveEngine=` `--fp16` `--memPoolSize=workspace:NMiB` `--iterations` `--warmUp` |
| **动态 shape** | `--minShapes/--optShapes/--maxShapes`（三者必须一起给） |
| **⚠️ 版本坑** | TRT 10 里 `--workspace` 已废弃，改名 `--memPoolSize`（我们踩过） |
| **看什么** | `Engine generation`（编译耗时）｜ `GPU Compute Time`（GPU 时间）｜ `Throughput`（吞吐） |
| **要能回答** | 编译一个 engine 需要哪些参数？编译失败了先看哪里？ |

## 4.4 算子融合 ⭐
| | |
|---|---|
| **是什么** | 把多个相邻算子合并成**一个内核**执行 |
| **为什么快** | GPU 瓶颈常在**内存带宽**而非算力；不融合就要"写回内存→再读出来" |
| **三种形式** | 纵向（Conv+BN+Relu）｜ **残差**（Conv+Add+Relu）｜ 横向（同形状并行） |
| **我的实测** | ONNX **49 个节点** → engine 只有 **26 层**；层名里能看到 `Conv + Add + Relu` |
| **怎么验证** | `trtexec --dumpLayerInfo` 或 `engine.create_engine_inspector()` |
| **要能回答** | ① 融合省掉的是什么开销？② 怎么量化融合程度？ |
| **⚠️ 易错点** | 以为"融合=算子变少=算力变高" —— 它省的是**数据搬运** |

## 4.5 内核自动调优 ⭐
| | |
|---|---|
| **是什么** | 同一层有多种内核实现，编译时**逐个实测、挑最快的** |
| **我的实测** | 编译日志里有 **4589 条 tactic 记录**（如 `ampere_scudnn_128x64_relu_xregs_large`） |
| **tactic 名字的含义** | `ampere`=架构 ｜ `128x64`=分块大小 ｜ `xregs_large`=寄存器策略 ｜ `implicit_gemm`=算法族 |
| **为什么编译要 30 秒** | 因为它真的在**跑一遍又一遍**做基准测试 |
| **关键后果** | 调优结果**与 GPU 型号强绑定** → engine 不能跨型号使用 |
| **要能回答** | 为什么编译 engine 要花 24~36 秒？ |

## 4.6 FP16 / INT8
| | |
|---|---|
| **FP16** | 指数范围与 FP32 相同，只是精度低 → **不需要额外信息**，加个 `--fp16` 就行 |
| **INT8** | 只有 256 档（-128~127）→ **必须知道数据分布**才能映射 → 需要校准 |
| **我的实测（FP16）** | 0.77 ms（8.2×）｜ engine 23.8 MB ｜ 最大误差 0.0322 |
| **我的实测（INT8）** | 0.61 ms（10.4×）｜ engine 11.7 MB ｜ 最大误差 **1.5186** ⚠️ |
| **精度代价曲线** | FP32→FP16 误差 ×1.8（温和）｜ FP16→INT8 误差 **×47**（跳变） |
| **要能回答** | ① FP16 为什么不用校准？② INT8 的"类别没变"为什么不等于"没影响"？ |

## 4.7 校准（calibration）⭐
| | |
|---|---|
| **是什么** | 用一批真实样本统计每层激活值的分布，算出最优的量化 scale |
| **流程** | 准备 100~500 张代表性图片 → 逐层统计直方图 → 算 scale → 存成校准表 |
| **我的实测** | 校准表只有 **2367 字节**（存的是每层的 scale 参数） |
| **⚠️ 工业界经典翻车点** | **校准数据不代表真实场景 → 精度崩得更狠** |
| **我的实测局限** | 只用了 12 张基础图 —— 这很可能就是 INT8 误差大的原因 |
| **要能回答** | ① 校准到底在算什么？② 校准集和测试集为什么必须分开？ |
| **⚠️ 易错点** | 用与真实场景不符的数据做校准；校准集混进测试集（报出的精度是假的） |

## 4.8 显式量化（Q/DQ）⬜
| | |
|---|---|
| **是什么** | 在模型里显式插入 Quantize/Dequantize 节点，标出每层的量化参数 |
| **为什么重要** | **TensorRT 10.1 之后官方推荐这种方式**，替代隐式校准 |
| **我的实测** | 运行时出现 `DeprecationWarning: Superseded by explicit quantization` |
| **要能回答** | 隐式校准（calibrator）和显式量化（Q/DQ）的区别是什么？ |

## 4.9 TensorRT Plugin ⬜
| | |
|---|---|
| **是什么** | 自己实现 TensorRT 不支持的算子，以插件形式接入 |
| **什么时候需要** | ONNX 里有 TRT 不认识的算子，且无法替换 |
| **要能回答** | 什么情况下才需要写 Plugin？（大多数时候不需要） |

## 4.10 CUDA Graph ⬜
| | |
|---|---|
| **是什么** | 把一串内核启动"录下来"，之后一次提交，消除逐个启动的开销 |
| **为什么重要** | 我们实测"GPU 时间 1.57ms vs 端到端 2.56ms"—— 差的 1ms 就是启动/主机开销 |
| **什么时候值** | 单次延迟敏感、且调用频繁的场景 |
| **要能回答** | 那 1ms 的主机开销，有哪几种办法减少？ |

## 4.11 Nsight 性能剖析 ⬜
| | |
|---|---|
| **是什么** | NVIDIA 的性能分析工具（Systems / Compute） |

# 六、边缘 AI 系统设计 ⭐

## 6.1 决策链 / 路由
| | |
|---|---|
| **是什么** | 一句话进来，先判断"该走哪条路"，再执行 |
| **前人的链** | ① 判难度（语义向量+kNN）→ ② RAG 查资料 → ③ 工具调用 → ④ 生成 |
| **核心思想** | **不是所有请求都值得动用大模型** —— 80% 的日常请求本地就能解决 |
| **我的实测** | 判难度只要 **60ms**（常驻服务），所以"每次都判一下"成本极低 |
| **要能回答** | 为什么"先判难度"这个设计能省大量成本？ |

## 6.2 RAG
| | |
|---|---|
| **是什么** | Retrieval-Augmented Generation：**让模型开卷考试** |
| **三步** | 离线：文档→切块→向量化→建索引 ｜ 在线：提问→检索 top-k→喂给模型 |
| **我的实测** | 99 块索引；问资料内的问题相似度 **0.649**，问资料外的问题 **0.376** |
| **⚠️ 核心认知** | **资料错，答案就错**，而且因为有出处反而更可信（我实测到它答出过期数字 98%） |
| **⚠️ 关键教训** | **不能靠相似度阈值判断"该不该查资料"**（闲聊 0.32~0.55 与资料 0.52~0.70 完全重叠） |
| **要能回答** | ① RAG 解决模型的哪两个硬伤？② 为什么不能用相似度阈值当闸门？ |

## 6.3 工具调用 / Agent
| | |
|---|---|
| **是什么** | 给模型一份"工具菜单"，它只负责**点菜**，代码负责**做菜** |
| **三步机制** | ① 模型输出 JSON（决定用哪个工具）→ ② 代码真正执行 → ③ 结果喂回模型总结 |
| **为什么裸模型不行** | 它没有时钟、没有网络、不能执行代码 |
| **我的实测** | 裸模型问"现在几点" → "我无法提供当前时间"；系统 → 真的查到了 15:52 |

# 七、工程方法论 ⭐（最容易被忽略，但最值钱）

## 7.1 性能测量
| | |
|---|---|
| **四条铁律** | ① **预热**（丢弃前几次）② **多次平均** ③ **看 percentile 不只看平均** ④ **固定输入** |
| **为什么** | 首次调用含加载/编译开销；平均值会掩盖尾延迟 |
| **要看哪些数** | GPU 计算时间（min/mean/median/P90/P99）｜ 吞吐 ｜ 端到端时间 |
| **我的实测** | trtexec 报 1.57ms（纯 GPU） vs Python 测 2.56ms（端到端）→ 差的 1ms 是主机开销 |
| **要能回答** | 为什么 trtexec 的数字和 Python 测的不一样？该信哪个？ |

## 7.2 精度验证
| | |
|---|---|
| **铁律** | **任何"快了 N 倍"的结论，都必须配上"精度掉了多少"** |
| **怎么测** | 固定一批输入 → 跑基线和优化版 → 比**最大绝对差** + **结果一致率** |
| **我的实测** | FP16 误差 0.0322（可接受）；INT8 误差 **1.5186**（top-1 没变但置信度明显畸变） |
| **要能回答** | 为什么"类别一致率 100%"不等于"INT8 无损"？ |

## 7.3 单位与口径 ⭐
| | |
|---|---|
| **为什么重要** | **单位错了，结论就反了** |
| **我的实例** | trtexec 的 `Throughput(qps)` 是"每秒多少次推理调用"，不是"每秒多少张图" |
| **后果** | 直接看 qps 会得出"batch 越大吞吐越低"的**完全相反**的结论 |
| **正确做法** | 真实图片吞吐 = **qps × batch** |
| **要能回答** | 看到任何吞吐指标，第一句该问什么？ |

## 7.4 预测 → 验证循环 ⭐
| | |
|---|---|
| **是什么** | 先写预测 → 再实测 → 对照 → 修正认知 |
| **为什么有效** | 读 AI/文档的解释会产生"**理解错觉**"（当时懂了，一周后不剩） |
| **我的战绩** | C3 batch 实验 **3/3 全对**；C4 INT8 实验 **1/3**（速度❌ 体积❌ 精度✅） |
| **错的收获** | 两次错分别补上了"每参数字节"和"峰值≠实际"两个认知 |
| **要能回答** | 为什么"预测错了"比"预测对了"更有价值？ |
